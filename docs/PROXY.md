# Garlic HTTPS/HTTP2 proxy — development transport

Архитектура: браузер → локальный HTTP CONNECT proxy → HTTPS/h2 входная нода → HTTPS/h2 выходная нода → TCP 443 сайта. Это отдельный потоковый транспорт; очередь HTTP-заданий Infinity остаётся отдельным компонентом и не используется для TCP-потока.

DNS: локальный UDP stub → POST /v1/dns по тому же HTTPS/h2 каналу → выходная нода → Cloudflare DoH, Google DoH при отказе/таймауте/SERVFAIL. Входная нода не обращается к публичным резолверам. CONNECT передаёт имя назначения выходной ноде, которая резолвит его системным резолвером; настройте системный DNS выходной ноды на 1.1.1.1 и резервный 8.8.8.8. Локальный stub не перехватывает весь DNS устройства: настройка ОС/приложений отдельная, отсутствие утечек не заявляется.

## Сертификаты и серверы

Нужны собственные домены, A/AAAA которых ведут на серверы. Для каждого сервера установить Caddy 2.10.2 или совместимую проверенную версию и запустить configs/Caddyfile с переменными GARLIC_DOMAIN и GARLIC_ACME_EMAIL. Внешние TCP 80/443 доступны для ACME/HTTPS. Let’s Encrypt выдаёт и обновляет сертификаты автоматически; в этой среде реальная выдача не проверена. Приватные ключи хранит Caddy вне исходников. Backend слушает только loopback, Caddy обращается к нему по h2c. HTTP/3 отключён. HTTP/1.x на внешнем интерфейсе получает 505.

На выходной ноде (Linux):

```sh
# GARLIC_PROXY_KEY передать из защищённых настроек окружения, минимум 32 байта.
# Не задавать GARLIC_EXIT_URL/GARLIC_EXIT_URLS — это конечная нода.
export GARLIC_DOH_URL=https://cloudflare-dns.com/dns-query
export GARLIC_DOH_FALLBACK_URL=https://dns.google/dns-query
./garlic-proxy server
```

На входной ноде (Linux):

```sh
# GARLIC_PROXY_KEY — ключ клиентов входной ноды.
# GARLIC_EXIT_KEY — отдельный ключ группы доверенных выходных нод.
export GARLIC_EXIT_URLS=https://exit-de.example.net,https://exit-nl.example.net
./garlic-proxy server
```

Имена example.net — заполнители. Ключи генерировать локально криптографическим генератором (например, openssl rand -hex 32) и передавать через защищённое окружение; не добавлять их в Git. Выходные ноды одного списка сейчас используют общий групповой ключ. Это временная модель доступа, не роли/пользовательские квоты/асимметричные подписи.

Входной backend и Caddy используют 127.0.0.1:8070. На каждом отдельном сервере конфигурация одинакова; менять только роль, ключи и домен. Если запускаете обе роли на одной машине, задайте разные GARLIC_PROXY_BIND и upstream в Caddy.

## Windows или Linux клиент

```sh
# GARLIC_PROXY_KEY передать из защищённых настроек окружения.
export GARLIC_ENTRY_URL=https://entry.example.net
# Опционально, для первоначального соединения без внешнего DNS:
export GARLIC_BOOTSTRAP_HOST=entry.example.net
export GARLIC_BOOTSTRAP_IP=203.0.113.10
./garlic-proxy client
```

Адрес 203.0.113.10 — заполнитель; нужен настоящий IP. Домен сохраняется в URL, SNI и проверке сертификата. Нельзя заменять домен IP-адресом или отключать проверку TLS. На Windows используйте `$env:NAME='value'` в PowerShell и `./garlic-proxy.exe client`.

Настроить браузер/приложение на HTTP proxy 127.0.0.1:1080. Поддержан CONNECT только к TCP 443, не SOCKS, UDP/QUIC или полный системный VPN. Обычный HTTP запрос к локальному proxy получает 405. DNS stub слушает UDP 127.0.0.1:1053; GARLIC_LOCAL_DNS_BIND меняет адрес/порт. Для системного порта 53 могут потребоваться права администратора. Автонастройки DNS ОС нет; Android VpnService и APK отсутствуют.

Внешний TLS использует rustls: точный ClientHello/HTTP2-профиль Chromium не реализован. При работе Chrome через CONNECT внутренний TLS сайта остаётся TLS Chrome; наружный канал до входной ноды от этого не становится Chromium. Chromium не скачивался и его код не переносился. Подделка User-Agent этого не исправляет.

TLS обеспечивает проверку сервера, шифрование и целостность каждого сегмента; Bearer-токены дают доступ к API. Отдельных цифровых подписей сообщений и общей сквозной аутентификации между клиентом и выходом пока нет. Входная нода доверенная. Нет фиктивного трафика Google или использования чужого домена.

## Проверки и ограничения

```sh
cargo test --workspace --locked
cargo build --release --workspace --locked
python integration-tests/smoke.py
# Дополнительно Python h2 4.4.1, OpenSSL и Caddy 2.10.2:
CADDY=/path/to/caddy python integration-tests/proxy_h2.py
```

TLS-тест создаёт временный CA и отдельный leaf-сертификат и удаляет их после прогона. Проверяет реальный TLS/ALPN h2, отказ неверного CA/ключа/HTTP1, full-duplex binary relay через mock exit, DNS stub, реальный код выходного DoH с mock Cloudflare/Google, запрет private target. Публичный Internet egress, реальные ACME, Windows runtime и Android не проверены.

TCP-потоки ограничены 128 слотами на сервер/клиент. DNS — общий серверный лимит и 64 клиентских запроса. Новые туннели выбирают exit round-robin. Автоматического переподключения потока или replay нет. Нет измеряемого выбора по здоровью, idle timeout на сервере, полного drain, управляемой ротации ключей, rate limit per user или мобильной интеграции. Клиент ограничивает поток одним часом. Приватные/локальные IP назначения и порты кроме 443 блокируются; для внутренней сети потребуется отдельная явно разрешённая политика.

Не объявлять production-ready или реализацией полного исходного ТЗ.
