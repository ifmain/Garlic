# Сборка Garlic для Linux x86-64

На входной ноде `garlic-dns` принимает сессии клиентов, хранит сетевой каталог и распределяет потоки. На выходной ноде `garlic-infinite-storage` обслуживает прямой маршрут, подключается к входу как исполнитель Relay v2 и синхронизирует учётные записи. `garlic-relay-worker` подходит для выходной ноды, которая обслуживает только Relay v2. Архив содержит также `garlic-coordinator`, `garlic-auth` и Linux-клиент `garlic-internal-network`.

На W `garlic-legacy-header` принимает конфигурацию прежнего адаптера с полями `listen`, `target`, `paths` и `response`. Указанный в конфигурации локальный слушатель используется между существующими ступенями legacy-транспорта.

`garlic-xui-legacy ПУТЬ_К_JSON` запускает локальные VLESS-входы из секций `s1` и `s2`. Каждая секция задаёт `listen`, адрес своего SOCKS5 `garlic_proxy` и UUID `local_vless_id`. Необязательная секция `trojan_grpc` задаёт `listen` и `accounts_file`. Вход Trojan gRPC использует пустое имя сервиса и прокси из секции `s1`. Без `sync` каталог загружается из файла, который подготавливает штатный управляющий скрипт W. Секция `sync` содержит HTTPS `origin`, `identity_file`, `keys_file` и `ca_file` для подписанного каталога T1. Шлюз сохраняет полученный каталог атомарно и проверяет срок его действия.

Из корня распакованного пакета проверить файлы командой `sha256sum -c SHA256SUMS`. Двоичные файлы лежат в `bin`. Файлы `entry.env.example` и `exit.env.example` показывают два варианта запуска. Для двух узлов на одном сервере назначить разные порты и каталоги состояния.

1. Скопировать бинарники в `~/.local/bin`, нужный unit-файл в `~/.config/systemd/user`, а соответствующий файл окружения в `~/.config/garlic/entry.env` или `~/.config/garlic/exit.env`. Указать свои HTTPS-адреса, пути и сертификаты. Имя в сертификате должно совпадать с адресом сервиса. Файл CA выхода должен доверять сертификатам входа и самого выхода.
2. Создать каталоги состояния по путям из `entry.env` и `exit.env`. Для новой сети создать ключи инфраструктуры командой `garlic-auth keys init ПУТЬ_К_КЛЮЧАМ v1`. Сохранить одну копию ключей на каждом узле этой сети. Для уже существующей сети использовать её ключи, состояние и отдельную идентичность каждой ноды.
3. Создать базу на новом входе командой `garlic-auth users init ПУТЬ_К_БАЗЕ`. Команда `garlic-auth users add ПУТЬ_К_БАЗЕ ИМЯ --password-stdin` получает пароль со стандартного ввода. Для административной записи задать роль через `garlic-auth users role ПУТЬ_К_БАЗЕ ИМЯ admin`.
4. Выполнить `systemctl --user daemon-reload`. Запустить `systemctl --user enable --now garlic-entry.service` на входе и `systemctl --user enable --now garlic-exit.service` на выходе. Проверить состояние командой `systemctl --user status garlic-entry.service` или `systemctl --user status garlic-exit.service` и сообщения соответствующей службы через `journalctl --user -u ИМЯ_СЛУЖБЫ`.

На сервере без пользовательского systemd переменные из соответствующего файла можно задать существующему менеджеру процессов и запускать бинарник напрямую. У пользовательских служб запуск до входа пользователя зависит от настройки linger на сервере. Автозапуск на рабочих узлах проверяется отдельно.

Если на T1 TLS проходит через локальный nginx с `proxy_protocol on`, использовать `GARLIC_TRUST_LOOPBACK_PROXY_PROTOCOL=1`. Координатор принимает заголовок PROXY v1 от соединений с loopback. TLS без такого заголовка доступен на том же порту.

На выходной ноде `GARLIC_USER_SYNC_INTERVAL_MS` задаёт интервал синхронизации аккаунтов. Значение 5000 мс совпадает со снимками S1, S2 и Амстердама. При резервном копировании состояния Rust сохранять базу и соседний файл метаданных репликации `accounts.json.replication.json`.

Для прямой службы хранения по схеме W использовать `GARLIC_DIRECT_ONLY=1` и пустой `GARLIC_DNS_URL`. Источник аккаунтов и реестр задаются отдельно через `GARLIC_ACCOUNT_AUTHORITY` и `GARLIC_NETWORK_UPSTREAM`. Когда `GARLIC_PUBLIC_URL` содержит DNS-имя, внутренние воркеры и очередь подключаются к адресу и порту локального слушателя с проверкой этого имени в TLS. Если для внутреннего трафика задан `GARLIC_LOCAL_STORAGE_URL`, они используют указанный адрес.

В комплект входят `probe ПОРТ ИМЯ`, `w-public-probe НОМЕР` и `w-legacy-probe СЛОТ НОМЕР`. Они проверяют HTTPS `/health` через прокси из прежней конфигурации W. Для этих утилит нужны `/usr/bin/curl` и доверенный сертификат в `pki/ca.pem` рядом с каталогом `bin` комплекта. Сценарии переключения сохранены отдельно в снимке W.

## Подключение существующей панели 3X-UI

На входной ноде задать `GARLIC_XUI_API_URL` с адресом локального API и конечной косой чертой. HTTP допускается для loopback. HTTPS сохраняет имя для проверки сертификата и направляет подключение на `127.0.0.1`. Прокси из окружения для этих обращений отключён.

Указать `GARLIC_XUI_SUB_URL` с публичным HTTPS-адресом подписок и конечной косой чертой, `GARLIC_XUI_W_NODE_ID` с числовым ID узла в панели и `GARLIC_XUI_TOKEN_FILE` с путём к файлу токена API. Доступ на чтение файла нужен учётной записи службы. Если адрес API не задан, `/v1/admin/legacy` отвечает `404`.

API использует существующие учётные записи Garlic. Применяются роль администратора и настройка обязательной аренды устройства. Для создания подписки выбирается один включённый Trojan-вход с указанным ID узла.

Служебный каталог `/v1/infra/legacy/accounts` включается настройками `GARLIC_XUI_W_IDENTITY` и `GARLIC_XUI_TROJAN_INBOUND`. Первое значение задаёт точный ID подписанного инфраструктурного удостоверения W. Второе задаёт числовой ID Trojan-входа этой ноды в 3X-UI. Каталог возвращает SHA-224 и сроки действия разрешённых ключей на две минуты. Запросы пользователя и других нод отклоняются.
